# Project config lives in data/projects.json, not in orchestrator.db

Project config is moving out of `src/projects.ts`, so that ysz runs on any machine and the human manages Projects from the Dashboard. It goes to `data/projects.json` (gitignored): a JSON array of `Project` objects with the same field names, with `repoPath` as an absolute path. There are three writers. The Dashboard writes it. The `/onboard-project` skill writes the file directly rather than through the HTTP API, because the Dashboard's API is for the human only. The human may also edit it by hand.

A Dashboard save reads the file from disk again, changes only the Project being saved, validates the result and writes it as tmp + rename. A write from the skill or the human therefore can only be lost if it lands in the milliseconds of a save, which is acceptable for one human per machine. At start, a missing file means no Projects, and the Dashboard offers to add the first one. An invalid file (bad JSON, a field of the wrong type, a duplicate name) stops ysz with the path, the Project and the field. It never falls back to an empty list, because a later Dashboard save would then overwrite the human's config.

While ysz runs, an edit takes effect without a restart: a Dashboard save at once, an edit from the skill or the human at the next poll (ysz re-reads the file each loop). A file that turns invalid while ysz runs does not stop it, since that would cut off live Runs: ysz keeps the last valid config, the Dashboard shows the path, Project and field, and Dashboard saves are refused until the file is fixed, for the same reason as above. A `repoPath` change on a Project with a live or In review Run is refused too (the Dashboard rejects the save; a hand edit keeps the old value for that Project and shows why), because the Run's claim heartbeat and its PR watch would follow the new path and lose the Ticket in the old repo.

A Project's name is its identity: Runs, pause state and history are kept under it, so it never changes. The Dashboard locks the name once a Project is saved; renaming means removing and adding, and a rename in the file is read the same way. Removing a Project follows the `repoPath` rule: refused while it has a live or In review Run (a hand edit keeps the Project in effect until those Runs end, and shows why), and at start ysz refuses to run if the file lacks a Project that still has one. Its ended Runs, Run logs and pause state stay under the old name, so adding the same name back brings them back; a Run action that needs the Project, such as Retry, is refused with a message instead. Two Projects with the same `repoPath` make the file invalid, like a duplicate name, since they would claim from one Ticket queue.

The Dashboard can edit every field, apart from the name lock and the `repoPath` rule above, `preflight` included, although `preflight` runs on the host. Whoever holds the Dashboard token counts as the human at the shell: the token lives in `data/`, which no sandbox mounts, the cookie is `HttpOnly` and `SameSite=Strict`, POSTs must carry the Dashboard's own Origin, and any host process can already edit `data/projects.json`. A `copyToWorktree` entry that is absolute or climbs out of the repo with `..` makes the file invalid, because it would copy a host file such as an SSH key into the clone the agent reads.

Onboarding is an explicit `onboarded: true` field, not the presence of `image`: every Project now shares `ysz-harness/agent`, so `image` is optional with that default, and a form field named "image" that silently turned a Project on would mislead. Adding a Project from the Dashboard is Onboarding: each save of a Project that is not yet onboarded runs the host checks, then its Smoke check in the background (`smokeCommand` is required there), and ysz writes `onboarded: true` itself once all pass. Zero Ready Tickets does not block it; a failed host check shows the command for the human to run, and the Dashboard runs nothing on the host to fix it. `onboarded` is the one field the Dashboard only shows, an exception to the rule above: ticking it would skip the Smoke check, and Pause already stops a Project. A hand edit may set it, since that is the human vouching at the shell; ysz keeps no record of a past Smoke check. A Project that arrives through the file without `onboarded` (the `/onboard-project` skill writes its entry before its own Smoke check) is not checked automatically, so the two never race; the Dashboard offers a Smoke check button, which onboards it on a pass. Editing an onboarded Project keeps it onboarded and does not rerun the Smoke check, which the button runs on demand; a failure advises Pause, as the skill does. One Smoke check runs at a time, outside the Run slots, since adding a Project is rare.

## Considered Options

- **A `projects` table in `data/orchestrator.db`**: it gives transactions and no lost updates, but the nested fields (`preflight`, `copyToWorktree`, the Check service) become JSON columns anyway, and both a hand edit and the skill would need SQL.
- **Reject a Dashboard save when the file changed since the form opened (mtime check)**: it closes the millisecond window, but costs a reload flow the Dashboard has no other use for.
- **`preflight` editable in the file only, or behind an extra confirmation in the Dashboard**: neither keeps out anyone who could not already edit the file, since only the human's browser holds the token.
- **`image` stays the Onboarding switch**: no change to the `/onboard-project` Spec, but the field means two things once every Project uses the same image.
- **A Project added from the Dashboard is onboarded on save, or only through `/onboard-project`**: the first drops the Smoke check, the second breaks "add a Project from the Dashboard and its first Ready Ticket is claimed".
- **ysz Smoke checks every Project that is not onboarded, whoever wrote it**: the skill could drop its own run, but would lose its fix rounds and race ysz on the same entry.
- **Skip invalid Projects and run the rest**: it hides a broken entry until the human wonders why its Tickets are never claimed.
